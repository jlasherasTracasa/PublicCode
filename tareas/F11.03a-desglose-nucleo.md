## Objetivo

1. Crea `split.rs` con las firmas de abajo. Nada de red ni de disco.
2. `split_prompt`: texto para el modelo fuerte con, en este orden: (a) la instrucción «Parte esta tarea en
   subtareas que un modelo pequeño pueda hacer leyendo solo la subtarea»; (b) las reglas: máximo 4 archivos
   en `## Toca`, objetivo con pasos numerados de al menos 300 caracteres, `## Firmas` si toca código,
   `## Tests` como `nombre: qué entra y qué se espera`, `## Contexto` no vacío, primero la lógica pura y
   después el cableado, ids `<id de la madre>` + letra de la `a` a la `h`; (c) el formato de cada archivo:
   cabeceras `<!-- acepta: … -->`, `<!-- modo: aislado -->`, `<!-- depende: … -->`, título `# id — título`,
   ficha `**Fase** … · **Ejecutor** haiku · **Talla** S` y las secciones; (d) el formato de respuesta: un
   bloque por subtarea, `<<<ID.md` en una línea, el contenido y `>>>` en otra; (e) `# Problemas del lint` con
   una línea `- [regla] mensaje` por problema; (f) `# Tarea` con `task.body`. Si `repair` es
   `Some((anterior, problemas))`, añade al final `# Tu respuesta anterior`, el texto y `# Corrige` con los
   problemas, uno por línea.
3. `parse_blocks`: devuelve `(nombre sin .md, contenido)` por cada bloque `<<<NOMBRE.md` … `>>>` (las dos
   marcas solas en su línea). Lo que quede fuera de los bloques se ignora. Un bloque sin cerrar se descarta.
4. `check_split`: valida los bloques y devuelve las tareas parseadas y la lista de problemas (vacía = vale):
   menos de 2 subtareas; id que no sea `<parent.id>` + una letra `a`–`h`; id repetido o que ya exista en
   `existing`; `parse_task` falla; dependencia que no es ni una tarea de `existing` ni una hermana anterior;
   y cada problema de `lint_task` como `<id>: [regla] mensaje`.
5. `lib.rs`: añade `pub mod split;`.

```rust
// crates/pcode-flow/src/split.rs
use crate::lint::LintIssue;
use crate::task::TaskDef;

/// Prompt para que un modelo fuerte parta `task` en subtareas.
pub fn split_prompt(task: &TaskDef, issues: &[LintIssue], repair: Option<(&str, &[String])>) -> String;
/// Bloques `<<<NOMBRE.md … >>>` de una respuesta: (nombre sin extensión, contenido).
pub fn parse_blocks(text: &str) -> Vec<(String, String)>;
/// Valida las subtareas propuestas. Devuelve las que parsean y los problemas (vacío = aceptadas).
pub fn check_split(
    parent: &TaskDef,
    blocks: &[(String, String)],
    existing: &[TaskDef],
    exists: &dyn Fn(&str) -> bool,
) -> (Vec<TaskDef>, Vec<String>);
```

## Ejemplo (entrada y resultado esperado)

```
parse_blocks("hola\n<<<T1a.md\n<!-- acepta: true -->\n# T1a\n>>>\n<<<T1b.md\nx\n>>>\n")
  → [("T1a", "<!-- acepta: true -->\n# T1a"), ("T1b", "x")]
check_split(madre T1, [("T1a", válida), ("T1b", válida que depende de T1a)], …) → (2 tareas, [])
check_split(madre T1, [("T1a", válida)], …) → (1 tarea, ["hacen falta al menos 2 subtareas"])
check_split(madre T1, [("X9", válida), ("T1b", válida)], …) → problemas contiene "X9: el id debe ser T1 seguido de una letra de la a a la h"
```

## Tests (con estos nombres)

- `prompt_lleva_tarea_problemas_y_formato`: el prompt contiene el cuerpo, `[objetivo]` y la marca `<<<`
- `prompt_de_reparacion_incluye_la_respuesta_anterior`: con repair aparecen `# Corrige` y el problema
- `lee_dos_bloques`: la entrada del ejemplo da dos pares con su contenido sin las marcas
- `bloque_sin_cerrar_se_descarta`: un `<<<T1a.md` sin `>>>` da lista vacía
- `dos_subtareas_validas_pasan`: dos tareas que pasan el lint dan cero problemas
- `una_sola_subtarea_no_vale`: un solo bloque da el problema de «al menos 2 subtareas»
- `id_que_no_es_de_la_madre`: el id X9 da el problema del ejemplo
- `subtarea_que_no_pasa_el_lint`: una subtarea sin objetivo da un problema que empieza por su id y lleva `[objetivo]`
