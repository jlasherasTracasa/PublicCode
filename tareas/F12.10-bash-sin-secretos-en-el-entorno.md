# F12.10-bash-sin-secretos-en-el-entorno — Tool `bash`: no heredar las variables de entorno con secretos (`*_API_KEY`, `*_TOKEN`…)

## Objetivo

Hoy las órdenes que lanza el agente heredan TODO el entorno de `pcode`, incluidas las claves de los
proveedores (`ANTHROPIC_API_KEY`…): un `env` o `echo $OPENAI_API_KEY` las manda al modelo y a la
transcripción.

1. En `bash.rs` añade la función pura `secret_env_names` (firma abajo). Un nombre es secreto si, en
   mayúsculas, termina en `_API_KEY`, `_APIKEY`, `_TOKEN`, `_SECRET`, `_PASSWORD` o `_PASSWD`, o es
   exactamente `API_KEY`, `TOKEN`, `SECRET` o `PASSWORD`, o contiene `SECRET_KEY` o `CREDENTIALS`; y NO
   está en `allow` (comparación sin distinguir mayúsculas). Devuelve los nombres originales, en el orden
   de entrada.
2. Añade `scrub_env` (firma abajo): llama a `cmd.env_remove(nombre)` por cada nombre de
   `secret_env_names(names, allow)`.
3. En `Bash::call`: construye la orden en una variable (`let mut c = shell_command(cmd);`), llama a
   `scrub_env(&mut c, &nombres, &permitidas)` y sigue con la cadena de siempre (`c.current_dir(…)…`).
   `nombres` = los nombres de `std::env::vars_os()` que sean UTF-8 válido; `permitidas` = el valor de
   la variable `PCODE_ENV_PERMITIR` partido por comas (sin espacios; vacío si no existe). Así el
   usuario puede dejar pasar, por ejemplo, `GITHUB_TOKEN`.
4. Tests en el `mod tests` de `bash.rs` con el prefijo `entorno_`. Para probar `scrub_env` sin tocar
   el entorno del proceso de tests: crea `let mut c = shell_command("echo \"[$PCODE_PRUEBA_TOKEN]\"");`,
   ponle la variable con `c.env("PCODE_PRUEBA_TOKEN", "valor")`, llama a `scrub_env` y ejecuta
   (`c.output().await`): la salida debe ser `[]`. Estos tests van tras `#[cfg(unix)]`.

## Firmas (cópialas tal cual)

```rust
// crates/pcode-tools/src/bash.rs
/// Nombres de variables de entorno que parecen secretos y no están en `allow`.
pub fn secret_env_names(names: &[String], allow: &[String]) -> Vec<String>;

/// Quita de la orden las variables de entorno con secretos (no se heredan ni las puestas a mano).
pub fn scrub_env(cmd: &mut tokio::process::Command, names: &[String], allow: &[String]);
```

## Ejemplo (entrada y resultado esperado)

```
secret_env_names(&["PATH", "ANTHROPIC_API_KEY", "GITHUB_TOKEN", "HOME", "db_password", "TOKENIZERS_PARALLELISM"], &["github_token"])
  → ["ANTHROPIC_API_KEY", "db_password"]
```

## Tests (con estos nombres)

- `entorno_detecta_nombres_de_secretos`: el ejemplo devuelve exactamente esos dos nombres
- `entorno_lista_permitida_sin_mayusculas`: `GITHUB_TOKEN` con `allow = ["github_token"]` no se quita
- `entorno_no_toca_variables_normales`: `PATH`, `HOME`, `CARGO_HOME` y `TOKENIZERS_PARALLELISM` no son secretos
- `entorno_scrub_quita_la_variable`: una orden con `PCODE_PRUEBA_TOKEN` puesta a mano imprime `[]` tras `scrub_env`
- `entorno_scrub_respeta_las_permitidas`: con `allow = ["PCODE_PRUEBA_TOKEN"]` la misma orden imprime `[valor]`

## No hagas

- No uses `std::env::set_var` en los tests (necesita `unsafe`, prohibido fuera de `pcode-sandbox`)
- No cambies `shell_command` ni `shell_argv`: las usan otros módulos que sí necesitan el entorno completo
- No toques los tests que ya existen
